# Sequence 383: serialize campaign execution and recovery

The sequence-382 report fix exposed a lifecycle race worth closing before any real campaign is eligible to run. Campaign state used atomic file replacement and digest checks, but independent campaign owners did not serialize the transition from a validated `next_trial_id` through executor completion. Recovery could also see the durable in-progress marker while its executor was still live and classify it as a process-death interruption.

The campaign now acquires the repository's native private POSIX `flock` around creation/re-entry, recovery, report generation, and the complete trial execution/state update. The lock file is opened relative to the verified private campaign directory with no symlink following, and its ownership, type, link count, and permissions are checked. Platforms without the native lock fail closed. Holding the lock for the full executor interval means another owner waits until either the trial is durably completed or the process exits; after a process exit, existing interruption/no-retry handling remains authoritative.

The adversarial regressions start a trial, hold its executor open, and concurrently attempt reconstruction through a second owner; reconstruction waits and then sees the completed receipt. A second test terminates a child process while it owns the lock, then proves the parent can recover the durable in-progress marker as terminal interrupted/no-retry state.
